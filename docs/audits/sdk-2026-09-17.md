# Audit du SDK Tuta — 17 septembre 2026

## Décision

Un rebase sur la release officielle récente est utile, mais **ne suffit pas à rendre le bridge compatible avec le déchiffrement AEAD des attributs**. Le Rust possède les primitives nécessaires, mais son décodeur d'entités n'y fait toujours pas appel. Le même manque subsiste sur `master` au commit audité.

L'explication « l'InvalidDataSizeError de #37 vient de l'AEAD et sera corrigée par un rebase » n'est donc pas établie. L'audit reproduit aussi exactement cette erreur avec un champ optionnel vide, un cas que le TypeScript officiel traite explicitement. Il faut distinguer ces deux problèmes.

## 1. AEAD : primitives présentes, intégration absente

Le commit officiel [81f115f75f](https://github.com/tutao/tutanota/commit/81f115f75fe408480ec2322d3b495df1eb344a49), intégré le 3 juin (date auteur : 24 avril), introduit le chiffrement AEAD des attributs derrière un déploiement progressif. Cette date de commit ne démontre pas quand un compte particulier a reçu le nouveau format.

Le TypeScript de la release distingue :

- le format CBC historique ;
- AEAD v2, avec clé de groupe versionnée et nonce KDF ;
- AEAD v3, avec clé de session ;
- les données associées dérivées du domaine et du chemin de l'attribut.

Sources : [formats](https://github.com/tutao/tutanota/blob/aea5846b93a1412451e885bf99002401c3b087e8/src/platform-kit/crypto/encryption/symmetric/SymmetricCipherVersion.ts), [sélection du décodeur](https://github.com/tutao/tutanota/blob/aea5846b93a1412451e885bf99002401c3b087e8/src/platform-kit/crypto/instance-pipeline-crypto/decryption/InstanceDecryptor.ts), [décodeurs de champs](https://github.com/tutao/tutanota/blob/aea5846b93a1412451e885bf99002401c3b087e8/src/platform-kit/crypto/instance-pipeline-crypto/decryption/ValueDecryptor.ts).

Dans le Rust officiel récent :

- `crypto-primitives::AeadFacade` sait chiffrer et déchiffrer les enveloppes v2/v3 ; des primitives AEAD existaient déjà dans notre base de mai, mais leur format a évolué depuis.
- `EntityFacadeImpl::decrypt_and_parse_value` appelle toujours `GenericAesKey::decrypt_data` pour les champs chiffrés.
- `GenericAesKey::decrypt_data` choisit seulement AES-128/AES-256 CBC. Il ne reçoit ni données associées, ni contexte KDF, ni sélection de format AEAD.
- Aucun appel à `AeadFacade` ou `AeadSubKeys` n'existe dans le code du SDK Rust de la release, hors bibliothèque de primitives. La présence de champs `_kdfNonce` dans les modèles générés ne constitue pas leur prise en charge cryptographique.

Sources : [décodeur d'entités, ligne 401](https://github.com/tutao/tutanota/blob/aea5846b93a1412451e885bf99002401c3b087e8/tuta-sdk/rust/sdk/src/entities/entity_facade.rs#L401), [décodeur générique, ligne 39](https://github.com/tutao/tutanota/blob/aea5846b93a1412451e885bf99002401c3b087e8/tuta-sdk/rust/crypto-primitives/src/key.rs#L39), [primitives AEAD](https://github.com/tutao/tutanota/blob/aea5846b93a1412451e885bf99002401c3b087e8/tuta-sdk/rust/crypto-primitives/src/aead_facade.rs).

**Preuve exécutée :** pour chacun des formats v2 et v3, les primitives officielles génèrent un chiffré synthétique et le déchiffrent correctement. Transmis au décodeur d'attribut du même SDK, ce chiffré produit `InternalSdkError: MacError`. Il s'agit d'une incompatibilité reproduite, pas de la reproduction du mail du contributeur.

Entre la release 359 et le `master` audité, les seuls changements sous `tuta-sdk/rust` concernent trois fichiers générés du modèle `sys`. Passer directement à `master` ne corrige donc pas ce chemin.

## 2. Une autre cause reproductible de l'InvalidDataSizeError

`Body.text` et `Body.compressedText` sont des champs chiffrés optionnels (`ZeroOrOne`). Lorsqu'un de ces champs contient la chaîne JSON vide `""` :

1. Le `JsonSerializer` Rust la décode en un tableau d'octets vide. Son traitement spécial des chaînes vides ne couvre que les champs obligatoires (`One`).
2. Le décodeur d'entités tente de déchiffrer ce tableau.
3. La primitive CBC renvoie `InvalidDataSizeError`, car elle reçoit moins de 16 octets.

Le TypeScript officiel traite explicitement le cas `ZeroOrOne` + `""` en renvoyant `null`, avec un avertissement. Le commentaire mentionne les changements historiques de cardinalité. Ce comportement existait déjà dans le TypeScript de la base de mai.

Sources : [parseur Rust, lignes 75–97](https://github.com/tutao/tutanota/blob/aea5846b93a1412451e885bf99002401c3b087e8/tuta-sdk/rust/sdk/src/json_serializer.rs#L75), [garde de taille CBC, ligne 554](https://github.com/tutao/tutanota/blob/aea5846b93a1412451e885bf99002401c3b087e8/tuta-sdk/rust/crypto-primitives/src/aes.rs#L554), [traitement TypeScript, ligne 365](https://github.com/tutao/tutanota/blob/aea5846b93a1412451e885bf99002401c3b087e8/src/platform-kit/instance-pipeline/CryptoMapper.ts#L365).

**Preuve exécutée :** passage d'un objet `Body` synthétique par le véritable `JsonSerializer`, puis le décodeur d'entités du SDK officiel. Une chaîne vide dans chacun des deux champs reproduit `InternalSdkError: InvalidDataSizeError`. Les mêmes objets avec `null` passent.

Ce parseur est inchangé entre notre base et la release récente ; la logique de déchiffrement concernée est également inchangée. Un rebase ne contient donc pas le correctif de ce cas.

**Limite :** aucun mail, token ou compte réel n'a été utilisé. Les journaux de #37 ne donnent ni le chemin de l'attribut en échec, ni sa longueur. Le défaut est démontré ; son implication dans l'incident du contributeur reste à confirmer. L'erreur seule ne prouve pas une origine AEAD.

## 3. Ce qu'apporterait réellement le rebase

- Actualisation des modèles `sys`, `tutanota` et `storage`.
- Actualisation du format des primitives AEAD et de leurs vecteurs de compatibilité.
- Ajout upstream de l'archivage de mails.
- Changements d'API à adapter : `Iv` devient `InitializationVector`, et `Versioned`/`VersionedAesKey` changent de module. Le bridge importe actuellement `Iv` dans `tuta.rs` et `store.rs`.

Les définitions des champs des types `Mail`, `MailDetailsDraft`, `MailDetailsBlob`, `MailDetails`, `DraftData`, `SendDraftData`, `File` et `MailSet` ne changent pas entre les deux modèles examinés. Les augmentations globales de versions de modèle ne démontrent donc pas une réparation des formats de corps de mail.

Une simulation Git à trois voies (`git merge-tree --write-tree <fork> <release>`) trouve un conflit textuel dans un seul fichier, `mail_facade.rs`, dans les tests MOVE/Archive. Cela suggère une intégration textuelle abordable, **pas une compilation garantie** : les imports renommés et les constructeurs de tests doivent aussi être adaptés. Aucun rebase ni build d'un fork fusionné n'a été effectué.

## 4. Ordre recommandé

1. **Corriger le cas des champs optionnels vides** dans un patch SDK séparé, en suivant la sémantique TypeScript et avec un test du parseur jusqu'au décodeur. Ajouter au diagnostic le nom/chemin de l'attribut et la longueur du chiffré, sans contenu ni clé, pour départager les erreurs de #37.
2. **Rebaser sur la release 359** et conserver nos ajouts nécessaires. Valider la compilation, les tests et les opérations du bridge ; ne pas présenter cette étape comme une résolution automatique d'AEAD.
3. **Porter l'intégration AEAD des entités**, en réutilisant les primitives officielles : sélection v1/v2/v3, dérivation et version des clés, nonce KDF, données associées et chemins des agrégats. Valider avec les vecteurs officiels, le rejet des données modifiées et des exemples complets d'entités, y compris les anciens formats. Auditer aussi le chemin d'écriture.
4. Automatiser ensuite les tentatives de mise à jour upstream. La CI de version détecte les refus HTTP 474 ; des tests de formats cryptographiques doivent couvrir l'autre frontière.

Ces résultats ne justifient pas encore une réécriture du bridge autour d'un processus TypeScript. Ils justifient de traiter explicitement le SDK Rust comme du code partiellement maintenu par le projet, et d'évaluer le coût du port de la couche d'entités avant de choisir une autre architecture.

Le mainteneur annonçait déjà le 3 juillet vouloir s'éloigner du SDK Rust : [commentaire upstream](https://github.com/tutao/tutanota/pull/10854#issuecomment-4874477285). Les PR 10854, 10870 et 10871 sont fermées sans fusion ; `SDK_PRS.md` les indique encore ouvertes et doit être actualisé lors du chantier SDK.

## Reproduction et périmètre

Le patch joint `sdk-2026-09-17-reproduction.patch` ajoute trois tests d'audit au SDK officiel. **Ils passent lorsqu'ils reproduisent les défauts décrits** ; ce ne sont pas des tests attestant de la compatibilité du SDK.

```sh
git -C tuta-repo worktree add --detach /tmp/tuta-sdk-audit aea5846b93a1412451e885bf99002401c3b087e8
git -C /tmp/tuta-sdk-audit apply /chemin/vers/sdk-2026-09-17-reproduction.patch
cargo test --manifest-path /tmp/tuta-sdk-audit/Cargo.toml -p tuta-sdk --lib audit_ -- --nocapture
```

Résultat : 3 tests passent, 300 autres tests filtrés. Observations : AEAD v2/v3 accepté par les primitives mais rejeté par le décodeur ; chiffré court rejeté avec `InvalidDataSizeError` ; champs optionnels `Body` vides rejetés avec la même erreur, contrôles `null` acceptés.

Audit réalisé dans un worktree temporaire. Aucun changement au SDK épinglé, aucune modification du code du bridge, aucun accès à un compte Tuta et aucun push. Ce rapport et le patch de reproduction sont les seuls livrables ajoutés au dépôt principal.
